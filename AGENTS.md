# Инструкции для разработки

Этот файл фиксирует согласованный стек и правила разработки сервиса «Календарь звонков». Продуктовые требования и пользовательские сценарии описаны в [README.md](./README.md).

Реализованы главная страница, создание типов событий по ключу управления и публичный каталог. React и FastAPI связаны через сгенерированный SDK; PostgreSQL, Alembic, генерация и задачи mise подключены. Выбор времени и бронирование реализуются следующими срезами спецификации #10. Фактические команды и настройки описаны в [README.md](./README.md).

## Назначение и границы проекта

- Одна установка обслуживает одного организатора и один общий календарь. Типы событий различаются id, названием, описанием и длительностью; их занятость общая.
- Организатор создаёт типы по ключу `ORGANIZER_ACCESS_TOKEN`, гость открывает публичный каталог или ссылку на тип. Ключ передаётся как Bearer только защищённым операциям; клиент хранит его в памяти, после обновления вводит заново. При отсутствующей настройке доступ закрыт.
- Расписание: будни 09:00–18:00 в `Europe/Moscow`, окно — сегодня и следующие 13 локальных дат, старты через 30 минут. Время отображается в часовом поясе календаря.
- Гость выбирает свободный слот, вводит имя, email и необязательный комментарий, затем получает подтверждение на экране.
- Полноценных аккаунтов, личных кабинетов, редактирования типов и расписания, отмены и переноса встреч нет.
- Внешние календари, письма и автоматическое создание видеозвонков не входят в первую версию.

## Стек технологий

| Область | Технологии |
| --- | --- |
| Фронтенд | React, TypeScript, Vite |
| Данные API на фронтенде | Сгенерированный TypeScript SDK, Fetch, TanStack Query |
| Описание API | TypeSpec с HTTP-моделированием через `@typespec/http` |
| Генерация OpenAPI | `@typespec/openapi3`, целевая версия OpenAPI 3.1 |
| Генерация клиентского SDK | Orval |
| Бэкенд | Python, FastAPI, Pydantic 2 |
| Генерация транспортных моделей Python | datamodel-code-generator |
| Доступ к БД | SQLAlchemy 2 asyncio, psycopg 3 в асинхронном режиме |
| База данных | PostgreSQL в Docker Compose |
| Миграции | Alembic |
| Версии инструментов и общие задачи | mise |
| Python-зависимости и виртуальное окружение | uv |
| JavaScript/TypeScript-зависимости | npm |

Версии инструментов закреплены в `mise.toml`, PostgreSQL — в `compose.yaml`, библиотеки — в `pyproject.toml`, `package.json` и соответствующих lock-файлах. Обновляй версии согласованно и проверяй совместимость всей цепочки генерации.

## API-контракт и генерация

Источником API-контракта является TypeSpec. Обязательная цепочка генерации:

```text
TypeSpec → @typespec/openapi3 → OpenAPI 3.1
                                ├─ Orval → TypeScript SDK → React
                                └─ datamodel-code-generator → Pydantic 2 → FastAPI
```

- В TypeSpec описывай операции, параметры, тела запросов, ответы и ошибки. Версию OpenAPI 3.1 указывай явно в настройках генератора.
- Генерируй SDK и Pydantic-модели из одного OpenAPI-документа, полученного из TypeSpec. Автоматически сформированная FastAPI схема не является источником для генерации SDK.
- Клиентский SDK обязателен: он должен содержать типы и функции HTTP-запросов, а также интеграцию с TanStack Query. Фронтенд обращается к API через этот SDK.
- Обработчики FastAPI, бизнес-логику и ORM-модели реализуй вручную. Сгенерированные Pydantic-модели описывают транспортные данные API.
- Сгенерированные файлы вручную не редактируй. Меняй TypeSpec или настройки генераторов и выполняй генерацию заново.
- При изменении API сначала обновляй TypeSpec, затем OpenAPI, SDK и Pydantic-модели, после чего согласуй реализацию сервера и фронтенда с контрактом.
- Проверяй соответствие реализации FastAPI каноническому контракту из TypeSpec, включая запросы, ответы и коды ошибок.

## База данных, бронирование и время

- Все обращения к БД в обработчиках API выполняй асинхронно: `async def`, `create_async_engine`, `AsyncSession`, psycopg 3 async.
- Выдавай каждому запросу отдельную `AsyncSession` и закрывай её после использования. При параллельных задачах используй отдельную сессию для каждой задачи.
- Выполняй бронирование в транзакции. На уровне PostgreSQL обеспечь запрет пересечений бронирований любых типов через exclusion constraint по полуоткрытым интервалам; предварительная проверка не заменяет это ограничение.
- При конфликте бронирования возвращай описанную в контракте ошибку с HTTP-статусом `409 Conflict`. Фронтенд должен предложить выбрать другое время.
- Исключай занятые и прошедшие слоты из доступных. Проверяй доступность и актуальность слота на сервере в момент подтверждения.
- Не раскрывай имена, email и комментарии других гостей через публичные страницы и API.
- Храни моменты начала и окончания бронирований в PostgreSQL как `timestamptz`. В приложении используй даты и время с часовым поясом; для хранения и сравнения ориентируйся на UTC.
- Храни часовой пояс календаря отдельно как идентификатор IANA, например `Asia/Makassar`, и отображай время в нём. Учитывай переходы часовых поясов при обработке локальных дат и интервалов.
- Любое изменение структуры БД оформляй миграцией Alembic.

## Окружение и команды разработки

- Используй mise для фиксации версий Python, Node.js и uv, настройки переменных окружения и запуска общих задач.
- Версии инструментов задавай в `mise.toml`. uv должен использовать Python, выбранный через mise, для создания виртуального окружения проекта.
- Веди Python-зависимости через uv в `pyproject.toml` и `uv.lock`.
- Веди JavaScript/TypeScript-зависимости через npm в `package.json` и `package-lock.json`. TypeSpec и Orval устанавливай как локальные зависимости разработки.
- Храни lock-файлы в репозитории. Установка зависимостей при обычной настройке окружения и в CI должна воспроизводить закреплённые версии.
- Для установки зависимостей используй обычные задачи mise с явными вызовами uv и npm.
- PostgreSQL запускай через Docker Compose.

Основные задачи mise:

| Задача | Назначение |
| --- | --- |
| `mise run setup` | Установить зависимости из lock-файлов |
| `mise run generate` | Сгенерировать OpenAPI, TypeScript SDK и Pydantic-модели |
| `mise run dev` | Запустить фронтенд и бэкенд для разработки |
| `mise run check` | Выполнить проверки стиля, типов, тесты и проверку актуальности генерации |

Эти задачи реализованы. Дополнительно доступны `db:up`, `db:down`, `migrate`, `generate:check`, `test:unit` и `test:integration`. Общая проверка требует отдельную PostgreSQL-базу, заданную через `TEST_DATABASE_URL`. При изменении задач обновляй порядок запуска и переменные окружения в [README.md](./README.md).

## Формат коммитов

- Используй Conventional Commits: `type: краткое описание` или `type(scope): краткое описание`. Область изменений (`scope`) необязательна, например `api`, `web` или `db`.
- Выбирай тип по смыслу изменений: `feat` — новая функциональность, `fix` — исправление ошибки, `docs` — документация, `test` — тесты, `refactor` — рефакторинг без изменения поведения, `perf` — оптимизация производительности.
- Для остальных изменений используй `style` — форматирование кода, `build` — сборка и зависимости, `ci` — CI, `chore` — обслуживание проекта, `revert` — отмена коммита.
- После двоеточия ставь пробел; описание должно кратко передавать суть изменения.
- Несовместимые изменения отмечай `!` перед двоеточием, например `feat(api)!: изменить формат ответа`, и поясняй последствия и способ перехода в теле сообщения с префиксом `BREAKING CHANGE:`.

Примеры:

```text
feat(api): добавить создание календаря
fix(db): исключить двойное бронирование слота
test: добавить HTTP smoke-тест запуска
docs: описать настройку окружения
```

## Проверки качества

- Перед коммитом запускай `mise run lint` (Ruff, проверка форматирования Python и ESLint). Git-хук `pre-commit` выполняет эту команду автоматически после `mise run setup` или `mise run hooks:install`; он проверяет весь рабочий каталог и не исправляет файлы.
- Используй одинаковые версии инструментов и команды проверок локально и в CI.
- Проверяй актуальность OpenAPI, SDK и Pydantic-моделей повторной генерацией и сравнением с сохранёнными результатами.
- Проверяй типы, стиль и соответствие FastAPI контракту, полученному из TypeSpec.
- Покрой тестами создание типов событий, публичный каталог, доступ организатора, получение доступных слотов, успешное бронирование, конфликт бронирования, отказ для прошедшего слота и отсутствие чужих персональных данных в публичных ответах.
- Проверяй одновременные попытки забронировать один слот: успешной должна быть только одна запись, остальные должны получить `409 Conflict`. Проверку выполняй с PostgreSQL.
- Проверяй работу часовых поясов, границы дат и переходы летнего времени.
- После изменений запускай проверки, соответствующие их объёму. Указывай, что было проверено, и явно отмечай проверки, которые выполнить не удалось.
- Сохраняй учебную инфраструктуру Хекслета: не изменяй, не удаляй и не переименовывай [hexlet-check.yml](./.github/workflows/hexlet-check.yml), не переименовывай репозиторий. См. [инструкции к автоматическим тестам](./.github/workflows/README.md).
