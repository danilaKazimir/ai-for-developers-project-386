# Гарантия отсутствия пересечений бронирований в PostgreSQL 17

Дата проверки: 4 ноября 2026 года. Исследование для билета
[«Какая гарантия PostgreSQL исключает пересечения при конкурентной записи?»](https://github.com/danilaKazimir/ai-for-developers-project-386/issues/6)
карты [«Типы событий и общая занятость организатора»](https://github.com/danilaKazimir/ai-for-developers-project-386/issues/2).

Это факты для будущего решения о протоколе бронирования. Область общей занятости,
модель организатора и политика повторов здесь не утверждаются. Код приложения,
миграции и автоматические тесты не создавались.

## Что даёт гарантию

PostgreSQL 17 умеет запрещать пересечения на уровне БД через exclusion constraint
с оператором пересечения диапазонов `&&`. Для моментов времени подходит
`tstzrange` — диапазон `timestamp with time zone`. Ограничение действует при записи,
поэтому предварительный запрос свободного времени не является источником
гарантии. Официальный пример PostgreSQL запрещает пересекающиеся бронирования
помещений. [Range Types: Constraints on Ranges](https://www.postgresql.org/docs/17/rangetypes.html#RANGETYPES-CONSTRAINT)

`UNIQUE(slot_id)` запрещает повтор одного идентификатора, а
`UNIQUE(event_type_id, starts_at)` — равные пары. Разные идентификаторы или начала
10:00 и 10:30 не равны даже при пересечении интервалов. Это следствие семантики
`UNIQUE`, которая сравнивает значения указанных столбцов, а не занятое время.
[Unique Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)

## Границы времени

Полуоткрытый диапазон `[начало, конец)` включает начало и исключает конец;
конструктор `tstzrange(starts_at, ends_at, '[)')` задаёт это явно. Для временных
диапазонов нельзя рассчитывать на автоматическое приведение произвольных границ
к `[)`: `timestamp` рассматривается как непрерывный тип.
[Range bounds and constructors](https://www.postgresql.org/docs/17/rangetypes.html#RANGETYPES-INCLUSIVITY)

Следствия определения `&&` как наличия общих элементов:

| Первый интервал | Второй интервал | Пересечение |
| --- | --- | --- |
| `[10:00, 11:00)` | `[10:30, 11:00)` | Да |
| `[10:00, 11:00)` | `[10:00, 10:30)` | Да |
| `[10:00, 11:00)` | `[09:30, 11:30)` | Да |
| `[10:00, 11:00)` | `[11:00, 11:30)` | Нет |

В таблице подразумеваются одна дата и одна шкала времени. Это вывод из определений,
а не результаты выполненного SQL-эксперимента.
[Range operators](https://www.postgresql.org/docs/17/functions-range.html#RANGE-OPERATORS-TABLE)

`timestamptz` хранит момент в UTC и не сохраняет исходный IANA timezone. Поэтому
сравнивать нужно реальные моменты с явным смещением/часовым поясом, а правила
преобразования рабочего расписания и IANA timezone хранить отдельно. Одинаковый
момент с разными смещениями не становится разным занятым временем.
[Time Stamps](https://www.postgresql.org/docs/17/datatype-datetime.html#DATATYPE-DATETIME-INPUT-TIMESTAMPS)

## Область общей занятости

Ниже формы SQL-ограничений для сравнения возможностей, не миграция проекта.
`starts_at` и `ends_at` предполагаются столбцами `timestamptz`.

| Вариант будущей модели | Форма ограничения |
| --- | --- |
| Единственный общий ресурс для всех бронирований | `EXCLUDE USING gist (tstzrange(starts_at, ends_at, '[)') WITH &&)` |
| Свой ресурс у каждого организатора | `EXCLUDE USING gist (organizer_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)` |

`EXCLUDE` не позволяет паре строк дать `TRUE` по всем перечисленным сравнениям.
Во второй форме конфликт означает одновременно равного организатора и
пересекающееся время; разные организаторы могут занимать одно время. Если добавить
в сравнения `event_type_id WITH =`, разные типы перестанут конфликтовать. Следовательно,
для общей занятости типов такой разделитель не выражает требуемую гарантию.
Ограничение относится к строкам одной защищаемой таблицы: раздельные таблицы
бронирований по типам с отдельными ограничениями не дают общей проверки между ними.
Это вывод из определения табличного `EXCLUDE`.
[CREATE TABLE: EXCLUDE](https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-EXCLUDE)

Для диапазона поддержка GiST встроена. Для равенства обычных скалярных ключей
(например, `integer`, `bigint`, `uuid`, `text`) в том же GiST обычно используют
расширение `btree_gist`. Оно устанавливается в нужной БД через
`CREATE EXTENSION btree_gist`; расширение trusted, для установки достаточно права
`CREATE` на БД при наличии файлов расширения на сервере. В варианте только с
диапазоном `btree_gist` не требуется. Само расширение не является гарантией:
нужен `EXCLUDE`, использующий его операторный класс.
[btree_gist](https://www.postgresql.org/docs/17/btree-gist.html),
[Range indexing](https://www.postgresql.org/docs/17/rangetypes.html#RANGETYPES-INDEXING)

Требования к данным для такой формы: обязательные начало, конец и ключ ресурса,
положительный интервал `starts_at < ends_at`; если нужны только конечные встречи,
отдельно запрещаются значения бесконечности. `NULL` в сравнении исключения не
считается `TRUE`, а пустой диапазон ни с чем не пересекается. Поэтому один
`EXCLUDE` не заменяет `NOT NULL` и проверку корректности интервала. `CHECK`,
читающий другие бронирования, не поддерживается как надёжное межстрочное ограничение.
[Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html),
[Range functions](https://www.postgresql.org/docs/17/functions-range.html#RANGE-FUNCTIONS-TABLE)

## Что происходит при конкуренции

Официальный исходник PostgreSQL 17.11 описывает проверку exclusion constraint:
после вставки выполняется поиск конфликтующих индексных записей; если
конкурирующая вставка/удаление ещё выполняется, проверка ждёт её завершения
и повторяется. Если конфликт остаётся, запись завершается ошибкой. Возможен
deadlock двух одновременно вставляющих транзакций: PostgreSQL прерывает одну.
Следовательно, нельзя обещать, что каждый проигравший запрос обязательно получит
именно `exclusion_violation` с первой попытки.
[PostgreSQL 17.11: execIndexing.c, комментарий Exclusion Constraints и повтор проверки](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/executor/execIndexing.c#L27-L50)

Для двух пересекающихся записей одного ресурса ограничение не допускает фиксации
обеих, в том числе без предварительного `SELECT` и при обычном `READ COMMITTED`.
Если первая транзакция откатится, её запись не должна окончательно блокировать
вторую; если зафиксируется, вторая должна завершиться конфликтом после проверки
или обработки транзакционной ошибки. Это следствия описанного ожидания и
повторной проверки. Успешный `INSERT`/`flush` ещё не равен подтверждённой встрече:
успех должен учитывать завершение транзакции. Для `DEFERRABLE` проверка вообще
может откладываться до конца транзакции; `NOT DEFERRABLE` — значение по умолчанию.
[PostgreSQL 17.11: check_exclusion_or_unique_constraint](https://github.com/postgres/postgres/blob/REL_17_11/src/backend/executor/execIndexing.c#L776-L862),
[Constraint timing](https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-DEFERRABLE),
[Session transaction framing](https://docs.sqlalchemy.org/en/21/orm/session_basics.html#framing-out-a-begin-commit-rollback-block)

## Как отличать ошибки

PostgreSQL рекомендует проверять SQLSTATE, а не локализованный текст сообщения.
Имя ограничения передаётся отдельным диагностическим полем для ошибок класса 23.
[PostgreSQL Error Codes](https://www.postgresql.org/docs/17/errcodes-appendix.html)

| SQLSTATE | Значение | Что известно для протокола |
| --- | --- | --- |
| `23P01` | `exclusion_violation` | Конфликт нужного ограничения занятости при совпадении его имени и таблицы/схемы |
| `23505` | `unique_violation` | Нарушение уникальности, само по себе не доказательство пересечения |
| `23503`, `23514`, `23502` | Foreign key, CHECK, NOT NULL | Иные нарушения целостности |
| `40001` | `serialization_failure` | Нужна обработка повтора полной транзакции |
| `40P01` | `deadlock_detected` | Возможен при конкуренции; не доказывает занятую встречу |

В psycopg 3 доступны `Error.sqlstate`, `Error.diag.constraint_name`,
`diag.table_name`, `diag.schema_name`; `ExclusionViolation` соответствует `23P01`
и наследует `IntegrityError`. SQLAlchemy оборачивает DB-API исключение в своё
исключение и предоставляет исходное через `orig`. Поэтому распознавание конкретной
занятости может опираться на SQLSTATE и заранее именованное ограничение, а не на
любое `IntegrityError`. Недоступные диагностические поля не следует угадывать.
[psycopg errors](https://www.psycopg.org/psycopg3/docs/api/errors.html),
[SQLAlchemy DBAPIError / StatementError.orig](https://docs.sqlalchemy.org/en/21/core/exceptions.html#sqlalchemy.exc.StatementError.orig)

После ошибки БД транзакцию требуется откатить; продолжение запросов в упавшей
транзакции не является повтором. При `40001` и обрабатываемом `40P01` повторяется
вся транзакция, включая проверки и вычисление значений. PostgreSQL не гарантирует
успех следующей попытки. Только повторная проверка/запись может установить,
превратился ли временный конфликт в занятую встречу. Лимит повторов и ответ при
исчерпании остаются вопросом будущего протокола; массово переводить эти ошибки
в HTTP 409 как подтверждённую занятость нельзя.
[Serialization Failure Handling](https://www.postgresql.org/docs/17/mvcc-serialization-failure-handling.html),
[psycopg Transactions management](https://www.psycopg.org/psycopg3/docs/basic/transactions.html)

## Альтернативы exclusion constraint

| Механизм | Условия корректности и ограничения |
| --- | --- |
| Блокировка общей существующей строки ресурса | Все писатели сначала берут одну и ту же блокировку `FOR UPDATE`, затем отдельным запросом при `READ COMMITTED` заново проверяют пересечения и пишут в той же транзакции. Глобальному ресурсу нужна общая строка; ресурсу организатора — строка этого организатора. |
| Транзакционный advisory lock | Общий ключ на ресурс работает даже при отсутствии бронирований. Все писатели обязаны соблюдать один протокол ключей и удерживать блокировку до конца транзакции; БД не навязывает advisory lock произвольному писателю. |
| `SERIALIZABLE` | Проверка отсутствия пересечений и запись выполняются одной транзакцией; все пути, на гарантию которых рассчитывают, соблюдают этот режим и проверку. Предикатные блокировки выявляют опасные зависимости даже при пустой выборке; возможен `40001`, требуется повтор. Одна изоляция без проверки бизнес-правила не запрещает пересечения. |

Это альтернативные протоколы для обсуждения, выведенные из гарантий блокировок
и изоляции. `SELECT ... FOR UPDATE` только по найденным бронированиям недостаточен:
при пустом результате нет строки занятости, которую обе транзакции обязаны
заблокировать. Блокировка строки типа события также не объединит разные типы.
После ожидания нужен свежий снимок для проверки; перенос такого протокола на
`REPEATABLE READ` без отдельного анализа некорректен. Блокировка таблицы может
сериализовать запись ценой блокирования разных ресурсов. Источники:
[Row-level and advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html),
[Read Committed and Serializable](https://www.postgresql.org/docs/17/transaction-iso.html).

## Совместимость со стеком

В исходном checkout закреплены PostgreSQL 17.11, SQLAlchemy 2.1.6,
psycopg 3.3.6 и Alembic 1.20.1 (`compose.yaml`, `pyproject.toml`). Для API SQLAlchemy
проверена документация ветки 2.1 семейства 2.x; документация psycopg 3 сейчас
показывает 3.3.7. Обновлять зависимости для изложенных механизмов не требуется.

SQLAlchemy предоставляет `TSTZRANGE`, `Range` и `ExcludeConstraint`, включая
выражения, имя, GiST и настройку откладывания. `create_async_engine` с
`postgresql+psycopg://` выбирает асинхронный вариант драйвера. Каждый параллельный
запрос/участник проверки конкуренции использует отдельную `AsyncSession` и
транзакцию; одна сессия не предназначена для совместного использования задачами.
[PostgreSQL dialect](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#postgresql-constraint-types),
[psycopg async dialect](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#psycopg),
[AsyncSession with Concurrent Tasks](https://docs.sqlalchemy.org/en/21/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks)

Alembic имеет PostgreSQL-операцию `create_exclude_constraint` и возможность
выполнить SQL установки расширения. Документация предупреждает: обнаружение
отдельных добавлений/удалений `EXCLUDE` через autogenerate может не поддерживаться.
Будущую миграцию нужно явно проверить: расширение до ограничения, именованный
constraint, корректный downgrade и поведение на PostgreSQL. Автогенерация сама
по себе не подтверждает наличие гарантии.
[Alembic Operations](https://alembic.sqlalchemy.org/en/latest/ops.html#alembic.operations.Operations.create_exclude_constraint),
[Alembic autogenerate limitations](https://alembic.sqlalchemy.org/en/latest/autogenerate.html#what-does-autogenerate-detect-and-what-does-it-not-detect)

## Сценарии проверки будущей реализации

Это критерии для настоящего PostgreSQL 17 с применённой миграцией, не выполненные
тесты. Ожидания выведены из механизма выше. Для конкурентных сценариев нужны
независимые соединения/сессии и управляемые барьеры, а не последовательные запросы.

1. Одна бронь `[10:00,11:00)` отклоняет частичное пересечение `[10:30,11:00)`,
   полное совпадение и охватывающий интервал; имя constraint и SQLSTATE проверяются.
2. Соседние `[09:30,10:00)` и `[11:00,11:30)` принимаются.
3. Другой тип того же ресурса конфликтует точно так же. При варианте ресурса на
   организатора другой организатор может занять совпадающее время; при глобальном
   ресурсе пересекающиеся записи всех типов конфликтуют.
4. На изначально пустой таблице два участника проверяют отсутствие брони, затем
   одновременно вставляют пересекающиеся интервалы разных типов. После обработки
   допустимых транзакционных ошибок фиксируется ровно одна бронь; проигравший
   получает согласованный конфликт. Повторить для одинаковых интервалов и группы
   конкурентов. Сырые `40001`/`40P01` не должны ошибочно считаться `23P01`.
5. Первая транзакция держит вставку без commit: вторая конфликтующая ждёт.
   Commit первой приводит к конфликту второй; rollback первой позволяет второй
   успешно записать бронь. Варианты с отсроченной проверкой проверяются на commit.
6. Параллельные смежные интервалы и разные ресурсы в соответствующей модели
   допускают обе фиксации; ошибка целостности другого constraint не маскируется
   сообщением о занятом времени.
7. Равные моменты с разными UTC-смещениями конфликтуют. Проверяются полночь и
   переход DST после серверного преобразования локального времени в моменты.
8. Пустые/обратные интервалы, `NULL` и запрещённые моделью бесконечности
   отклоняются; прямой SQL в обход API также не сохраняет пересекающиеся брони.

Исследование ограничено чтением первичных источников и локальных манифестов.
SQL на PostgreSQL и проверки приложения не запускались. Выбор области занятости,
конкретного ограничения/протокола, HTTP-ошибки и политики повторов остаётся в карте.
